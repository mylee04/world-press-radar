# Clinic and FBM artifact retention

The owner authorized removal of unnecessary Clinic Signals and FBM backups, inactive deployment artifacts and stale temporary exports on October 19, 2026. Running services, original application data and news collection history remain outside the deletion scope. Nothing in this policy starts collection, restores data or restarts a service.

## Continuous cleanup

Oracle installs `shared-project-retention.py` as `/usr/local/sbin/shared-project-retention`. Without `--apply` it only previews. Apply uses a global maintenance lock, checks each candidate's inode/device/mtime again, rechecks the current release and excludes process paths. Descriptor-based `shutil.rmtree` unlinks release-local data symlinks without following them into original shared data. A fixture verifies this boundary. Removal receipts replace small per-scope files in `/var/lib/shared-project-retention`; the initial cleanup receipt is retained separately. Physical space recovery is measured by filesystem free space, because release hardlinks make summed folder sizes an unreliable estimate.

`shared-project-retention.timer` runs hourly with low CPU/I/O priority. The existing FBM backup script invokes its `fbm-backups` scope only after a successful standalone dump; its prior 30-day removal is replaced by the seven-copy rule. Clinic's existing backup function now defaults to three completed snapshots in both canonical local source and current server source. Existing backup schedules remain unchanged.

Clinic temp removal only targets exact old `tmp????????` names and the new `.city-inventory-*`, `.catalog-*`, `.residential-*` export prefixes in the shared data directory. Files must be at least one hour old, unopened and unchanged since planning. Cleanup must acquire the existing `.collection-worker.lock` inode; it never removes or replaces that lock and skips while the collector owns it. A `clinic-signals-ru-monitor.service` drop-in runs only the `clinic-temps` scope after the existing collector finishes or times out. This scope has a separate maintenance lock so a long release cleanup cannot make it miss the idle window. Both scopes still share the original collection lock for temp removal. The after-collector command ignores maintenance errors so cleanup cannot change the collector's existing result. It adds no collection run and requires no service restart.

Canonical and deployed Clinic `city_inventory.py`, `store.py` and `residential_leads.py` now assign the temporary name before serialization and unlink it in `finally`. Failed writes or replaces preserve the prior completed output. Nine focused cases cover success, JSON failure and replace failure across the three actual writer functions. Forced termination can bypass Python cleanup, so the stale-file sweep remains necessary. Clinic's preexisting 20-minute collection timeouts are a separate reliability issue; this work does not change that timeout or source-collection behavior.

Seven retention fixtures cover the kept sets, original/unknown preservation, process references, symlink safety, changed candidate refusal, the busy collection lock and preservation of manual audit metadata. A separate tiny fixture ran the actual Clinic backup function five times and confirmed its default retains three while leaving the original fixture database unchanged. No full application test suite, real collection, full production database scan or restore was performed. Private source diffs, previews and before/after receipts are under `output/news-quality/shared-storage-cleanup-20261019` and `output/news-quality/shared-disk-retention-20261019`.

Small Clinic manual audit records and the FBM original change archives remain. The filesystem gained 43,037,560,832 bytes, a measured 40.08 GiB, during this first pass. Its new after-completion hook acquired the released worker lock and removed those six stale files, recovering another 1,201,446,912 bytes (1.12 GiB). The hook's receipt showed no skipped candidates. Fresh or open temporary files remain protected and become eligible only when stale and the collection lock is free.

The Clinic web app, FBM web app and FBM operator service retained identical active PIDs and start times across cleanup. Clinic's four live SQLite files retained their original inodes, and the current release stayed unchanged. The news ledger retained identical size and modification time, its wrapper hash matched, and its regular timer was unchanged. No application service was manually restarted and no additional collection was launched. Hourly artifact retention and the existing private capacity warning timer remain enabled.

## Source-version storage, November 1 Chicago / November 2 UTC

The recent completed-day storage sample showed about 2.40 GiB/day net shared filesystem decline, including all projects and cleanup, versus approximately 0.105 GiB/day news ledger growth. These are physical measurements with different per-cycle and daily windows; they are not an exact allocation of all shared writes. Bounded inventory found roughly 27.2 GiB allocated to Clinic's `opening-evidence/snapshots`, `reviewed-openings/snapshots` and `reviewed-contacts/snapshots`. Their 109,531 mostly HTML files are original source versions, not disposable UI pagination caches. Deleting those versions would violate the existing source-history policy.

Clinic's canonical Python storage code now preserves the original logical `SHA256.html` identity while storing new HTML as deterministic gzip. Readers accept either representation and validate decoded size and the original SHA256. Repeated content does not rewrite the existing version or its timestamp. PDF/JSON storage and transferred evidence packages keep their existing plain-file compatibility. Source facts, check dates, raw hash references, manual captures and database history retain their meanings. The same six Python files were installed in the current release and two retained rollback alternatives after confirming that their prior Python versions matched exactly. Web assets and active services were not restarted. The canonical Clinic folder has no Git repository; source code before-images, new file hashes and compatibility records remain in the private operation directory.

`scripts/clinic-snapshot-compactor.py` is installed as `/usr/local/sbin/clinic-snapshot-compactor`. It processes only exact lowercase SHA256 HTML filenames in those three snapshot roots. A verified gzip is published and reread before the redundant plain representation is removed, with UID/GID/permissions and file identity checked. Recent, changed, linked, oversized or unprofitable files are protected. Every source version remains recoverable; this is a representation change rather than expiration of evidence.

The system timer retries idle batches every two minutes. Default timer runs require the collector service to be inactive, and all runs require its original collection lock and a separate maintenance lock. The monitor's synchronous completion hook invokes `--after-collection` before the unit becomes inactive, so maintenance cannot steal the next collector's startup interval. That flag bypasses only the service-state check, never the locks or legacy-reader guard. Batches are capped at twenty seconds, 256 MiB input and 2,000 eligible files, with low CPU/I/O priority. Only small numeric latest/cumulative receipts remain in `/var/lib/clinic-snapshot-compactor`. Existing source collection schedules and the shared disk warning system remain in place.

Eight helper cases and eighty existing affected Clinic module cases passed. The compactor's four original cases and two startup-order cases passed without repeating a full application suite. A real server fixture confirmed that root-created gzip retained mode 0640 and that the Clinic service user restored the exact original hash. Production backlog progress must be read from the maintenance receipt; sample compression ratios of 15 to 22 percent are not a measured whole-tree saving.

The first production batch ran at November 2 04:23:15 UTC after the collector reached its preexisting twenty-minute timeout. In 13.29 seconds it compacted 1,209 files, preserving 268,332,128 decoded bytes in 54,493,303 gzip bytes and reclaiming 213,413,888 allocated bytes, about 203.5 MiB. The batch stopped at its input budget. The next existing collector invocation started after the completion hook at 04:23:28, with no manual restart. Historical backlog conversion continues in idle batches; the whole tree has not yet been converted. The Clinic collector's recurring timeout predates this storage change and remains a separate operational issue.

Separately, twenty unused physical `node_modules` directories from old news releases were removed under the news runner lock after current/rollback/private-dashboard dependencies, symlink closure, process references and unit paths were protected. Their measured allocation was 2,062,127,104 bytes, approximately 1.92 GiB. Observed filesystem availability rose from 92.28 to 94.21 GiB during that operation; concurrent writers limit causal interpretation of the net change. Release source, audit records, metadata, manifests and lockfiles remain. Reusing one of those old releases requires reinstalling its pinned dependencies. The live news ledger, current dependencies and active services were preserved. This cache recovery is a one-time gain, distinct from the ongoing Clinic storage change.

The private daily collection message now separates per-cycle ledger growth from measured shared filesystem net daily decline, labeling the sample duration and inclusion of other projects/cleanup. Its saved message was edited in place, rather than sending another copy. Future health checks from this reporter carry the inspection hint. Six affected collection-summary cases and five usage-summary cases passed; no extra collection or publisher audit ran.

Compression and bounded artifact cleanup slow growth but do not make permanent source-version and URL-identity retention finite. News URL identity and scope memory must not be expired silently: doing so would count returning URLs as new. At the cited cycle's 107.7 MiB, thirty comparable cycles would add about 3.15 GiB, a conditional estimate rather than a forecast guarantee. Long-term capacity still requires an explicit retention/archive budget or further lossless representation improvements. The 50 GiB floor is an execution guard, not a reserved filesystem partition.
